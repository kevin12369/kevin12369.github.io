# 排查一次「假超时」：127.0.0.1 上 8 个端口全部超时，服务却根本没开

## 前言

七个月。

我上一次在这个博客发文，是 2026 年 3 月 15 日，写一篇关于春节红包大战的复盘。写完之后又忙起来了，然后就没有然后了。

这七个月里它一直挂在 GitHub Pages 上，首页还是那十篇，最新的一篇永远是那篇复盘。每次我自己点进去看，都有一种「哦，还在」的复杂感觉——它没死，但也没在呼吸。

所以这次我决定重新开始，并且给自己定了一条规矩：**每一次排查，都要写成一篇复盘。**

技术这行有个很怪的毛病：故障处理完就过去了，下次遇到还是从头猜。但如果把「现象 → 排查 → 根因 → 处理 → 复盘」完整写一遍，下次就变成了肌肉记忆。

这条规矩的第一个考题，来得比我想象中快。

那天下午我坐在 Windows 前面，想确认本机的网络状态。我写了个小脚本，扫一圈常见端口——22、53、80、443、3306、6379、8080、8000——用 TCP 连一下，看哪些是通的。

结果出来的时候，我愣住了。

```
Host      Port Result    Ms
----      ---- ------    --
127.0.0.1   22 timeout 1511
127.0.0.1   53 timeout 1512
127.0.0.1   80 timeout 1503
127.0.0.1  443 timeout 1515
127.0.0.1 3306 timeout 1508
127.0.0.1 6379 timeout 1506
127.0.0.1 8080 timeout 1505
127.0.0.1 8000 timeout 1508
```

**八个端口，全部超时。**

可问题是，我明明知道 80 和 443 上没有服务在跑——那台机器上根本没起过 Web 服务。这种情况下连接应该「秒拒」：内核立刻回一个 RST，告诉我「这个端口没人接」。

它不该干等 1.5 秒才超时。

那 1.5 秒里，到底发生了什么？

---

## 第一层：先别急着怀疑服务

### 一个看起来很合理的结论

如果只扫 Windows 这一侧，最省事的解释是：「有防火墙在丢包（drop 而不是 reject），连接被静默吞掉，等不到回应只能超时。」

这个解释非常像真的。Windows Defender 防火墙的默认策略就是丢弃不匹配的流量，很多人在别的场景里被这个坑过。

### 但它和监听端口表对不上

我习惯在动手之前先看一遍「本机到底谁在听」。这一步差点被我跳过了——幸好我写了。

Windows 侧的监听表里，有这么几行：

```
LocalAddress  LocalPort Process                        PID
------------  --------- -------                        ---
127.0.0.1        5335 mihomo                       10672
127.0.0.1        7890 mihomo                       10672
127.0.0.1        7891 mihomo                       10672
127.0.0.1        7892 mihomo                       10672
```

`mihomo`——就是那个跑在 127.0.0.1:7890 的代理内核，Clash Party 用的就是它。

然后我注意到一件事：**这张表里，80、443、3306、8080、8000 一个都没有。** 它们确实没有服务在听。

所以「防火墙丢包」这个解释站不住脚：包要是被防火墙丢了，它不会精准地只放过 7890 那一组端口、而把我探测的八个全部拦下——那可是我**主动发起**的连接，方向都反了。

<Label>关键一步</Label>

排查的时候，**先确认现象本身是不是真的**。这八个 timeout，可能是环境制造出来的假象，而不是服务出了问题。

这一步如果跳过，我会顺着「防火墙」一路查到半夜，然后发现自己查错了方向。

## 第二层：环境变量里的陷阱

### 先看环境

我在 Windows 和 WSL 两侧都把环境变量打了一遍。WSL 这边的输出是这样的：

```bash
HTTPS_PROXY=http://127.0.0.1:7890
HTTP_PROXY=http://127.0.0.1:7890
NO_PROXY=172.31.*,...,10.*,192.168.*,127.*,localhost,<local>
http_proxy=http://127.0.0.1:7890
https_proxy=http://127.0.0.1:7890
no_proxy=172.31.*,...,10.*,192.168.*,127.*,localhost,<local>
```

全局代理开着，指向本机的 7890。这本身很正常，很多人为了科学上网都会这么设。

**但关键在于：我的机器上跑着 mihomo 的 TUN 模式。**

TUN 模式在网络层接管流量——它把网卡做成一个虚拟的三层设备，所有流量先经过它，再由它决定转发、拦截还是直连。对于要访问 127.0.0.1 的连接，代理内核会「接手」：它发现对方是本机，于是照例向 127.0.0.1:7890 建立一条代理连接，把我的请求交出去。

从外面看，我 connect 的是 127.0.0.1:80；内核这边接手的却是 7890 上的另一条连接。**原本该由内核回我 RST 的那个环节，变成了代理在另一条连接上等我回应。**

于是——超时。1.5 秒后我的脚本放弃，报 timeout。

<Card>
**「超时」和「拒绝」根本不是一回事：**

- **refused（RST）**：内核明确告诉你「这个端口没人听」。这是**有信息的失败**。
- **timeout**：没有任何回应。可能是网络不通、防火墙丢包，也可能是**有人在中间把连接接走了，但它不打算回你**。

排查时把这两者混为一谈，就会被带进最麻烦的方向。
</Card>

### no_proxy 的通配符为什么不管用

看到 NO_PROXY 里有 `127.*` 和 `localhost`，我的第一反应是「这不是已经排除了吗」。

但脚本用的 .NET `TcpClient`，根本不读 `no_proxy`——那玩意儿是 curl 和大多数 Unix 工具的约定，.NET 有自己的 proxy 配置。

于是我换成 curl 试。这次它认 `no_proxy`……吗？

<Collapse title="curl 的 no_proxy 只认精确主机名">
`no_proxy` 支持的写法是**精确域名**或**域后缀**，例如：

- `example.com` — 匹配该域名本身
- `.example.com` — 匹配所有以 `.example.com` 结尾的域名

而 `127.*` 这种写法，curl **不认**。IP 地址要么用精确匹配（`127.0.0.1`），要么用 CIDR（`127.0.0.0/8`，curl 7.86 起才支持）。

顺带一个惊喜：curl 其实还认 `<local>` 这个写法——名字起得很妙，意思是「所有不带点的主机名」。
</Collapse>

所以正确的写法是：

```bash
# 精确列出回环地址
export no_proxy=127.0.0.1,localhost

# 或者用 CIDR（curl 7.86+）
export no_proxy=127.0.0.0/8,localhost

# 单次调用临时绕过
curl --noproxy '*' http://127.0.0.1:8000/
```

<Aside>
**为什么是 `--noproxy '*'`？** 单引号里的星号是给 shell 看的，表示「这个参数不要做通配展开」，把星号原样传给 curl。curl 收到 `--noproxy '*'` 的意思是「所有主机都不走代理」。不加引号时，shell 会先尝试把星号展开成本地文件名；展开失败就把字面量传过去——在 bash 默认不匹配任何文件时也能凑效，但依赖这个行为就不太稳了。
</Aside>

## 第三层：WSL 里的三件怪事

Windows 侧说明白了，我换到 WSL 里继续看。WSL2 Ubuntu 24.04 是我最近拿来练手的 Linux 环境，一进去就撞上三件让人困惑的事。

### 一张网卡，还是两张？

```bash
$ ip -brief addr
lo               UNKNOWN        127.0.0.1/8 10.255.255.254/32 ::1/128
eth0             UP             192.168.3.85/24 fe80::acd0:d736:67a7:6e89/64
loopback0        UP
eth1             UP             192.168.3.133/24 fe80::8c5d:540a:6c45:dba5/64
```

我 Windows 上有以太网（192.168.3.85）和 WLAN（192.168.3.133），WSL 把它们**各自映射成了一张虚拟网卡**，所以 WSL 里是 eth0 加 eth1。

更麻烦的是路由：

```bash
$ ip route
default via 192.168.3.1 dev eth0 proto kernel metric 25
default via 192.168.3.1 dev eth1 proto kernel metric 45
192.168.3.0/24 dev eth0 proto kernel scope link metric 281
192.168.3.0/24 dev eth1 proto kernel scope link metric 301
```

**两条默认路由，同一个网关。** metric 25 比 45 小，所以流量走 eth0 出去。

<Label>这个坑在哪儿</Label>

Windows 上如果两张网卡连着同一个网关，路由表可能给出两条候选路径。而在 WSL 里，这意味着：**任何「网段通了没有」的判断都可能失真**——你 ping 通，不代表走了你以为的那条路。

排查网络问题时，先 `ip route` 把路由表看清楚，再谈结论。

### systemd 报错了

每次进 WSL，我都能看到这一行：

```text
wsl: Failed to start the systemd user session for 'kevin'. See journalctl for more details.
```

我 `/etc/wsl.conf` 里 `systemd=true` 是开着的，systemd 本身也跑起来了（我能看到 systemd-resolved 在工作）。挂掉的只是**用户级**的 systemd 会话，也就是 `systemctl --user` 这一类。

影响其实不大，但排查时很容易误导人：我要是想 `systemctl status` 某个用户服务，看到的会是「systemd user session unavailable」，然后一头雾水。生产环境里遇到的「systemctl 说服务没起来」，很可能就是这个坑的变体。

### DNS 在 10.255.255.254

```bash
$ ss -tulnp
tcp   LISTEN 0      1000   10.255.255.254:53         0.0.0.0:*
tcp   LISTEN 0      4096       127.0.0.54:53         0.0.0.0:*
udp   UNCONN 0      0        10.255.255.254:53         0.0.0.0:*
udp   UNCONN 0      0          127.0.0.54:53         0.0.0.0:*
```

53 端口确实在监听，只不过地址不是 127.0.0.1，是 **10.255.255.254**——WSL2 的 DNS 转发地址。

<Aside>
**为什么是 10.255.255.254？** WSL2 跑在轻量虚拟机里，Windows 侧的 DNS 解析器会被映射到这个虚拟地址，WSL 里的请求交给它，再由它转发给真正的 DNS 服务器。所以你在 WSL 里 `dig` 一个域名，实际是 Windows 在给你解析。
</Aside>

顺带说一句，这台机器上 `dig`、`traceroute`、`tcpdump` **都没装**：

```text
=== tool check ===
MISSING tcpdump
OK      curl -> /usr/bin/curl
OK      python3 -> /usr/bin/python3
OK      nc -> /usr/bin/nc
MISSING dig
MISSING traceroute
hint: sudo apt update && sudo apt install -y tcpdump net-tools iproute2 dnsutils traceroute
```

工具缺就装，这是最没有技术含量的一步，但它是一切的前提。

## 第四层：让它真正跑通一次

光诊断不算完。我想看到一次**完整成功**的链路：起一个服务，用客户端打它。

我起了个最简单的：

```bash
$ python3 -m http.server 8000 --bind 127.0.0.1 &
server pid: 505 (python3 -m http.server 8000)
```

然后用 curl 打，并且明确绕开代理：

```bash
$ curl -sS -v --noproxy '*' --max-time 5 http://127.0.0.1:8000/
*   Trying 127.0.0.1:8000...
* Connected to 127.0.0.1 (127.0.0.1) port 8000
> GET / HTTP/1.1
> Host: 127.0.0.1:8000
> User-Agent: curl/8.5.0
> Accept: */*
>
* HTTP 1.0, assume close after body
< HTTP/1.0 200 OK
< Server: SimpleHTTP/0.6 Python/3.12.3
< Date: Sun, 25 Oct 2026 03:50:22 GMT
< Content-type: text/html; charset=utf-8
< Content-Length: 515
```

200 OK，10 毫秒：

```text
http_code=200 time_total=0.010027s
```

对照着看，差别就很清楚了：

| | 之前（Windows 侧探测） | 现在（WSL 侧 curl） |
| --- | --- | --- |
| 目标 | 127.0.0.1 上的 80、443 等 8 个端口 | 127.0.0.1:8000（服务已启动） |
| 结果 | 全部 timeout，耗时约 1500ms | 200 OK，耗时 10ms |
| 说明 | 连接被代理接管，没人回我 | 直连成功，链路完整 |

**同一台机器，同一个回环地址，差别只在「有没有服务在听」和「有没有绕开代理」。**

### 抓包那一步，被跳过了

我原本还想把这次交互抓成 pcap，用 Wireshark 逐帧看三次握手。但 tcpdump 没装，而脚本里用的是 `sudo -n`（非交互模式，不弹密码提示），没缓存过 sudo 凭据就直接跳过了：

```text
=== 5. capture result ===
no pcap produced (sudo/tcpdump unavailable)
```

```bash
sudo apt update && sudo apt install -y tcpdump dnsutils traceroute
sudo -v        # 缓存一次密码，之后 sudo -n 才能用
```

这一块留个坑，下次补上。**说实话，承认「这一步我没做成」，比含糊过去更接近工程师该有的样子。**

## 最后想说的话

这次排查从头到尾没有遇到什么惊天动地的故障，可它让我把一条以前模糊的认知给掰清楚了：

**「连不上」是一个结论，不是一个现象。**

现象是「我发出去一个连接，没有得到回应」。连不上的原因可能是：链路不通、路由错了、防火墙丢包、服务没起、端口写错、DNS 解析到了别的机器……还有一种，是**根本没人真正参与过这次连接**——它被中间件接走了。

所以我现在的排查顺序是这样的：

<Card>
**我的排查清单（从下往上，逐层排除）**

1. **先确认现象是真的** — 换个工具、换个客户端再测一次。工具会骗人。
2. **看谁在监听** — `ss -tulnp` / `netstat -ano`，先搞清楚本机状态。
3. **看环境** — 代理、`no_proxy`、`HTTP_PROXY`、自定义路由表。这一步最容易被跳过，也最容易背锅。
4. **分层往下走** — 链路层（ARP / 网卡）→ 三层（ping / traceroute）→ 四层（nc / curl）→ 应用（状态码 / 日志）。
5. **最后才问「最近改了什么」** — 版本、配置、发布时间、变更单。

**一条判断原则：**

- **refused** = 内核明确说「没人听」→ 问题在服务侧
- **timeout** = 没人回应 → 问题在网络或中间设备（**也可能问题在你自己身上**）
</Card>

最后那句加粗的，就是我这次学到的。

写完这篇，我打算继续按这个节奏来：一次排查，一篇复盘。抓包那一环补上之后，大概还会有第二篇。
